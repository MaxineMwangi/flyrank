Ranking Content for Review Using Historical Performance and Freshness Signals

Maxine Mwangi · FlyRank ML Internship · Machine Learning track · October 2026

Abstract

This study investigates how a content team can prioritize pages for review when only a limited number of pages can be assessed in each cycle. The work focuses on Refresh / Content Opportunity Scoring and uses historical content-performance and freshness signals to produce a ranked review queue. The analysis uses the anonymized FlyRank dataset, constructs an observed decline-score outcome from the measured trend percentage, compares a two-signal baseline against a gradient-boosting regression model, and evaluates both approaches using a client-grouped train/test split. The final model and baseline are compared on the same held-out clients using NDCG@100, Precision@100, and Spearman correlation, with the exact values loaded from the capstone metrics file when available. The resulting ranking can be used as decision-support evidence to help a content team identify pages for manual review, while avoiding the claim that refreshing a page will necessarily improve its performance.

1Introduction and problem statement

Content teams often have more pages that could be reviewed than they have time to evaluate. A practical question is therefore which pages should be examined first when review capacity is limited. This project addresses that decision through a Refresh / Content Opportunity Scoring approach that ranks content according to signals associated with observed performance decline.

The research question is: Which content pages should be prioritized for review based on measured performance, content freshness, and search-position signals?

The objective is not to automate the decision to refresh a page. Instead, the objective is to provide a ranked queue that helps a content team decide where manual investigation should begin.

2Data

This work uses the anonymized FlyRank ML Internship dataset stored at data/raw/content_refresh_anonymized.csv. The dataset contains 30,000 content records and uses pseudonymized client and content identifiers. The available fields include historical 90-day performance measures, recent performance measures, content age, freshness information, search-position information, engagement measures, and trend information.

For this capstone, the analysis operates at the content-item level and uses client_id as the grouping variable. The observed trend percentage is converted into a temporary outcome proxy, decline_score = -trend_pct, so that larger values represent larger observed negative trends.

What was excluded, and why

Client and content identifiers are retained only for grouping, deduplication, and identification. They are not used as predictive features. The original trend_pct field is used only to construct the outcome proxy and is not included among the model features. Rows without a usable outcome or without the required model features are excluded from the modeling dataset. No client names, domains, URLs, or other identifying information are used in the analysis.

3Methodology

Assumptions

The analysis assumes that the historical content and performance signals provide useful information for prioritizing pages for review. It also assumes that pages from the same client may share characteristics, making client-level grouping important during validation. Finally, the ranking is treated as decision support rather than a causal estimate of the effect of refreshing content.

Label

The outcome used in this capstone is decline_score, constructed as the negative of the dataset's measured trend_pct. Consequently, a larger decline score represents a more negative observed trend. This is an observed-trend proxy rather than a genuinely future-window outcome, so the resulting ranking should not be interpreted as a guaranteed prediction of future traffic or ranking loss.

Features

Feature Why it is used
impressions_90d Represents measured search visibility accumulated over the available 90-day period.
clicks_90d Represents measured clicks accumulated over the available 90-day period.
content_age_days Represents how long the content has existed and provides an indication of content maturity.
days_since_last_update Represents how long the page has gone without an update and provides a direct freshness signal.
avg_position Represents measured average search position, with larger values indicating weaker search position.

Baseline

The baseline ranks pages using two signals: days_since_last_update and avg_position. Each signal is converted to a percentile score, with higher values treated as worse, and the two scores are combined using equal 50/50 weighting. The resulting baseline is associated with the reason code STALE_OR_LOW_RANK and the action label Refresh content.

Model

The machine-learning model is a HistGradientBoostingRegressor trained using the five features above. The model uses a maximum depth of 4, a learning rate of 0.05, and 200 boosting iterations. The model produces a continuous score that is used to rank pages from highest to lowest review priority.

Validation design and leakage checks

Validation uses a grouped 75/25 train-test split with client_id as the grouping variable. This prevents pages from the same client from appearing in both training and testing data. The model and baseline are evaluated on exactly the same held-out rows.

Three basic leakage checks are used. First, a feature-name screen checks that outcome-related or future-looking fields are not included among the model features. Second, a shuffled-label test randomly rearranges the outcome values and checks whether performance falls toward chance. Third, a too-good-to-be-true threshold flags unusually strong ranking performance for manual investigation.

Permutation importance is also used after model evaluation to inspect which of the five input features contributes most strongly to the fitted model's predictions. These checks provide safeguards against obvious evaluation problems, but they do not prove that the analysis is completely free from all possible forms of leakage or bias.

5Limitations and honest framing

These results are observed on one anonymized dataset and should therefore be treated as directional. They support content-review decisions but do not establish that a page will decline in the future or that refreshing a page will cause improved performance.

First, the outcome is based on an observed performance trend rather than a genuine future-window outcome. The current capstone therefore should not be interpreted as a production-ready forecasting model.

Second, the dataset represents a historical snapshot and cannot capture every factor affecting content performance, including changes in search demand, seasonality, competitor activity, content quality, technical issues, or external events.

Third, the analysis is observational. A high score indicates that a page deserves attention according to the available signals, but it does not demonstrate that taking the recommended action will improve the page.

Fourth, the model does not explain Google's ranking algorithm. Search position is treated as an observed performance signal rather than evidence about the internal operation of a search engine.

Finally, the ranked queue should be combined with human review. Pages may be incorrectly prioritized when their historical measurements are unusual, incomplete, seasonal, noisy, or affected by information that is not represented in the dataset.

6Ranked recommendations

The primary recommendation is to use the highest-ranked pages as the starting point for manual content review. The action label associated with the baseline is Refresh content, while the corresponding reason code is STALE_OR_LOW_RANK.

The ranking should be interpreted as a prioritization queue rather than an automatic action list. Before refreshing a page, the team should check whether the decline signal is meaningful, whether the content is still relevant, whether search demand has changed, and whether another explanation better accounts for the observed performance.

Priority Action Reason code What would make it wrong
1 Refresh content STALE_OR_LOW_RANK The page may be intentionally stable, seasonal, affected by changing search demand, or experiencing a decline caused by an external factor.
2 Refresh content STALE_OR_LOW_RANK The measured signals may not represent the current state of the page or may contain insufficient historical information.
3 Refresh content STALE_OR_LOW_RANK A high ranking score does not establish that refreshing the page will improve its future performance.

7Reproducibility

The project code is maintained in the public repository: github.com/MaxineMwangi/flyrank .
